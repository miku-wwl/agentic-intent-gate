## Installation and immutable dependency

Merge this dependency into an independent consumer's existing `pyproject.toml`:

~~~toml
dependencies = [
  "agentic-intent-gate @ git+https://github.com/miku-wwl/agentic-intent-gate.git@v0.3.0",
]
~~~

For the strongest pin, replace `v0.3.0` with the **full 40-character release commit SHA**
from the Release notes before locking the consumer. Never depend on a moving `main`
branch. Verify the annotated tag object and its peeled commit:

~~~powershell
git ls-remote https://github.com/miku-wwl/agentic-intent-gate.git refs/tags/v0.3.0 'refs/tags/v0.3.0^{}'
uv sync --python 3.13
uv run python -c "from importlib.metadata import version; import agentic_intent_gate.runtime as r; print(version('agentic-intent-gate')); print(r.__file__)"
uv pip check
~~~

The peeled commit must equal the full release SHA, installed metadata must report
`0.3.0`, and imports must resolve to the installed environment. Retain the consumer's
updated lockfile and direct-URL commit metadata. Release assets can alternatively be
downloaded from GitHub and checked against `SHA256SUMS.txt` before wheel installation.
No adjacent source checkout or editable/path dependency is required. AIG is not published
to PyPI; third-party dependencies may be downloaded from the configured package index.

## Changes since v0.2.0 and provider configuration

Ollama remains the default. New cloud providers are selected by trusted operator
configuration at startup, never by an Intent, Plan, model response, or HTTP request.
The optional working-directory `.env` file is read without interpolation. Process
environment values override the same keys in `.env`. Conflicting new and legacy
Ollama aliases are rejected rather than silently choosing one.

| Provider | Required configuration | Request contract |
| --- | --- | --- |
| Ollama (default) | `LOCAL_LLM_BASE_URL`, `LOCAL_LLM_MODEL`; or `AIG_LLM_BASE_URL`, `AIG_LLM_MODEL` | HTTP loopback, explicit port, `/v1/chat/completions` |
| `openai` | `AIG_LLM_PROVIDER=openai`, `AIG_LLM_MODEL`, `OPENAI_API_KEY` | Fixed `https://api.openai.com/v1/chat/completions`, JSON mode |
| `anthropic` | `AIG_LLM_PROVIDER=anthropic`, `AIG_LLM_MODEL`, `ANTHROPIC_API_KEY` | Native `https://api.anthropic.com/v1/messages`, one completed text block |
| `openai-compatible` | `AIG_LLM_PROVIDER=openai-compatible`, `AIG_LLM_MODEL`, `AIG_LLM_BASE_URL`, `AIG_LLM_API_KEY` | Operator-owned public HTTPS/443 endpoint, common chat fields |

Use `.env.example` and [Development](DEVELOPMENT.md#model-provider-configuration)
for complete settings. Choose a model that supports the documented wire format.
The bundled planning prompt remains specific to `service-demo`; an independent
domain supplies its own trusted `ModelProvider` through the public Runtime API.
Cloud selection sends the Intent to that provider. Keep credentials and sensitive
Intent data out of source, logs, screenshots, and release evidence.

Requests use one non-streaming attempt with a total deadline of at most 28 seconds,
64 KiB response-envelope and 16 KiB Plan-text limits, bounded output tokens, no
redirects, no ambient proxy configuration, and no repair, retry, or provider fallback.
Unsupported/refused/truncated/tool-call/malformed output fails closed. Cancellation
propagates while closing the response. Provider availability or model quality is not
proved by mocked transport tests.

## Consumer API, compatibility, and approval boundaries

No breaking public consumer API or persisted Action/schema changes relative to v0.2.0.
Existing v0.2.0 pins may remain in use; upgrading is an explicit consumer dependency
decision. The added runtime dependency is `python-dotenv`. This release leaves the
compiler, authorization, registry, schemas, execution ledger, consumer example, and
execution-budget implementation unchanged from v0.2.0.

Supported imports include:

~~~python
from agentic_intent_gate.runtime import (
    BoundCapabilityAuthorization,
    CapabilityVerifier,
    ExecutableRegistry,
    ToolBinding,
    ToolCapability,
    execution_budget_binding,
    open_runtime,
)
~~~

See the executable [consumer app](../examples/consumer/app.py) and
[public API example](ADAPTER_GUIDE.md#supported-consumer-api). Define one reviewed
startup-frozen binding, a closed bounded scalar argument schema, and one consumer-owned
executor/receipt store. Use the same binding in capability, registry, verifier, policy,
and receipt validation. Import the installed public Runtime; retain competition adapters,
credentials, policies, target allowlists, and external API details in the consumer repository.

Preserve this sequence:

Validated Plan -> persistent Run -> exact human approval -> trusted Action admission ->
independent authorization -> durable execution claim -> one bounded effect -> durable result.

Approval never dispatches an effect. One approved `SIDE_EFFECT` step is executable.
CAS, grant/specification binding, stable effect keys, idempotent command handling, and
fail-closed recovery remain mandatory. Interrupted or ambiguous effects become terminal
`Unknown`; neither restart nor refresh retries them. The example's scripted approval is
test consent, not an authenticated human approval flow.

Omitting `execution_timeout_seconds` preserves five seconds and legacy identities.
Above five, use a fresh reviewed base binding with `execution_budget_binding(binding, 15)`,
a fresh scope and separate private ledger/receipt identity, then pass
`execution_timeout_seconds=15` to `open_runtime`. The suffix and v3 compiler/specification
identity prevent old Actions from gaining longer authority. Do not migrate or relabel
persisted Actions or reuse grants across profiles. The maximum is fifteen seconds;
caller deadlines only shorten it. Reserve adapter time for verification/receipts and
transport time for claim/finish. The bundled Action HTTP parent deadline remains ten seconds.

PactLens, Open Agent, and other Hackathon consumers should update only their dependency
and lockfile first, inspect the installed public API, retain their trusted adapters and
approval gates, and run their own full acceptance suite before a separately authorized
live pilot. This release does not change or qualify any downstream repository.

## Operational limits

This is a local development/demo Runtime. Local bearer capabilities and approval endpoints
do not provide production user authentication. Trusted Python is not sandboxed. DNS/endpoint
ownership, provider retention and credential operations remain operator responsibilities;
configuration-time address checks do not prove resistance to DNS rebinding. Execution
deadlines are cooperative, cannot preempt blocking Python, and do not guarantee remote
exactly-once effects. There is no general plugin/MCP orchestration or public reconciliation
API. See [Security](SECURITY.md) for the complete trust model.
